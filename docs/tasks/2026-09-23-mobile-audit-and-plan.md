# Radar NG mobile audit and execution plan — 2026-09-23

Scope: the iOS and Android app in `frontend/`. That covers the Expo/React Native app plus the native Apple targets (Watch app, WidgetKit widget, CarPlay scene) under `frontend/targets/`. The backend is out of scope except where the app depends on its contract.

Audience: **the model that executes this plan.** It is written so that you can work through it without the audit conversation. Each task names the evidence (file:line at the audited tree), the change, how to verify it, and whether a human with a physical device must sign it off.

Audited tree: `master` @ `bdacbb9` plus the **uncommitted** working-tree changes listed in §1.4. Line numbers refer to that tree. Re-check them before editing, because earlier tasks will shift lines.

## 0. Rules of engagement (read first)

### 0.1 Guardrails — do not do these

1. **Never hand-edit `frontend/ios/` or `frontend/android/`.** Both are generated by `expo prebuild` and gitignored. Native changes go through config plugins (`frontend/plugins/`), `app.json`/`app.config.js`, or target sources (`frontend/targets/`).
2. **Do not change `CAROUSEL_WINDOW` in `frontend/src/lib/radarCarousel.ts` from 1** unless a human reports a passing physical-iPhone run of the checklist in Appendix A. Build-time overrides for testing are fine (task 4.2).
3. **Do not touch the CarPlay entitlement, provisioning, or Apple correspondence.** Apple CarPlay case 22361864 is open (`docs/carplay-review-22361864/`). Never send email and never edit `reply-draft.txt`. Never set `RADAR_CARPLAY=1` for a build that will be distributed.
4. **Do not rewrite git history, force-push, or delete the user's uncommitted work.** See decision D1.
5. **Do not publish anything**: no App Store Connect or TestFlight uploads, no Play Console uploads, no `eas submit`, and no backend deploys.
6. **Do not claim device verification you did not do.** Simulator, emulator and JS-export results are not physical-device results. The repo's QA docs are strict about this; keep that standard. Mark device-gated tasks as "ready for device QA", not "done".
7. **Stop and ask** when you reach a decision point marked **D#** (§5). Do not pick for the user.
8. Keep the project's existing principle of **truthful UI**: never show invented weather, health, or freshness values. Several tasks below exist because the UI still does.
9. **In SDK 57, `expo prebuild` deletes and regenerates `frontend/ios`** (`--no-clean` opts out). `bun run test:ios` runs a prebuild too. `frontend/ios/` currently holds two user Xcode export folders with IPAs: `radarng 2026-09-21 00-37-55/` and `radarng 2026-09-21 00-42-24/`. **Ask the user before the first prebuild** and suggest they move those folders out of `ios/`.

### 0.2 Working conventions

- Package manager: **bun** (`bun install --frozen-lockfile`, `bunx …`). Run app commands from `frontend/`.
- Work on one branch per phase (`mobile/phase-1-release-blockers`, …). Keep commits small and focused, and write messages in the style of `git log`. Push or open PRs only if the user authorizes it in your session.
- Keep code style consistent with neighbours: comment density, naming, and `StyleSheet.create` factories.
- Record durable decisions and verified root causes with Mink, per `AGENTS.md`: `mink note --project radar-ng --category projects --title "…" --body "…"`. Do not run bare `mink note --help`: it creates an empty note.

### 2.2 Apple (iOS/watchOS 27, Xcode 27, shipped 2026-09-14)

- **Toolchain.** Xcode 27 is 27A266a. **Verified locally**: `/Applications/Xcode.app` is 27.0 (27A266a), while `xcode-select -p` points at `/Applications/Xcode-27.0.0-Beta.6.app` (27A5252f). The build script's default `/Applications/Xcode-beta.app` doesn't exist on this Mac. Archive with the release Xcode (task 1.3). Beta builds are rejected in standard practice; that couldn't be confirmed on a current Apple page (UNVERIFIED). EAS Build has no Xcode 27 image yet ([Expo](https://docs.expo.dev/build-reference/infrastructure/)), so local archiving remains the path.
- **Scene lifecycle.** Required with the iOS 27 SDK (above). Expo 57.0.24 ships `ExpoAppSceneDelegate`/`ExpoReactNativeFactoryProvider` (**verified locally**). Research also reports an opt-in `ios.enableSceneSupport` for expo ≥57.0.23 that refuses to run when Info.plist already declares a scene manifest ([expo/fyi](https://github.com/expo/fyi/blob/main/ios-scene-lifecycle.md)). That key is **not present in the installed 57.0.24 packages** (UNVERIFIED), so read that document before relying on it. SDK 58 makes the scene lifecycle the default and generates `SceneDelegate.swift` + a manifest. Our CarPlay plugin's wholesale manifest/AppDelegate overwrite would collide with that; task 1.1 removes the collision.
- **iPhone apps become resizable with the iOS 27 SDK**, so orientation locks are only a preference ([Expo docs, SDK 58](https://docs.expo.dev/versions/v58.0.0/sdk/screen-orientation/)). Apple announced a new iPhone form factor ("iPhone Duo", 2026-10-23, iOS 27.1) ([Apple](https://developer.apple.com/news/?id=rfb1rooi)). `app.json` `orientation: "portrait"` is no longer a guarantee. See F-M4 and task 5.7.
- **Liquid Glass in iOS 27**: refreshed materials and tab/nav bars ([Apple](https://developer.apple.com/ios/whats-new/)). The `UIDesignRequiresCompatibility` opt-out is ignored with the iOS 27 SDK ([Apple](https://developer.apple.com/documentation/bundleresources/information-property-list/uidesignrequirescompatibility)); this app doesn't set it. A user transparency slider arrives *(secondary: MacRumors)*. Custom translucent chrome should respect Reduce Transparency (task 5.2).
- **CarPlay** ([Developer Guide, June 2026](https://developer.apple.com/download/files/CarPlay-Developer-Guide.pdf), [WWDC26 session 212](https://developer.apple.com/videos/play/wwdc2026/212/)):
  - Navigation apps must provide turn-by-turn directions with upcoming maneuvers, and the base map view may only draw the map. That is the known review risk behind case 22361864.
  - For **widgets in CarPlay**: `systemSmall` widgets appear automatically on iOS 26+. `widgetURL` only launches the app if the app is itself a CarPlay app. Widgets that rely on data-protection classes A or B fail while the phone is locked. `disfavoredLocations([.carPlay])` opts a widget out.
  - New APIs: `CPMapPanel` (iOS 27) and route/destination sharing (iOS 26.4).
- **WidgetKit**: a new `systemExtraLargePortrait` family on iPhone ([Apple](https://developer.apple.com/documentation/widgetkit/widgetfamily/systemextralargeportrait)). Not needed now.
- **watchOS 27**: Foundation Models and Vision on the watch ([Apple](https://developer.apple.com/watchos/whats-new/)). arm64 has been required since April 2026; the Watch target uses default architectures and complies.
- **Privacy manifests**: no 2026 changes found (UNVERIFIED). Each bundle that calls required-reason APIs needs its own manifest. The widget and Watch currently call none.
- **Location authorization**: no iOS 27 changes found (UNVERIFIED). **WeatherKit/MapKit**: nothing listed for 2026.

### 2.3 Android (16 / API 36 now; 17 / API 37 next)

- **Targeting API 36** ([behavior changes](https://developer.android.com/about/versions/16/behavior-changes-16)):
  - The edge-to-edge opt-out is gone. This makes F-A2 a real layout bug.
  - Predictive back is on by default, but `enableOnBackInvokedCallback=false` still opts out. `predictiveBackGestureEnabled: false` matches the SDK 57 template default.
  - On ≥600 dp screens, orientation and resizability locks are ignored; an opt-out exists until API 37 (F-A6).
- **Android 17 / API 37** (stable 2026-06-16; [behavior changes](https://developer.android.com/about/versions/17/behavior-changes-17)). When targeting 37:
  - The large-screen opt-out is removed.
  - A new **`ACCESS_LOCAL_NETWORK` permission** is required for LAN connections. That directly affects self-hosters using `http://<LAN-IP>`.
  - Certificate Transparency is on by default.
  - ECH is on for TLS.
  - No Play deadline for 37 has been announced. Record these as prerequisites for the eventual target bump.
- **Material 3 Expressive** is still experimental. No impact: the app has no native Android UI code.

## Appendix A — Physical-device checklist (human)

Run on a physical iPhone (iOS 27) and a physical mid-range Android phone. Use release builds, not debug.

1. Cold start with location allowed. Home shows content within ___ s, and the correct city label appears. Repeat in airplane mode: the persisted forecast shows with "Updated … ago".
2. Location denied: an honest fallback label, and never "My Location".
3. Radar tab: the first frame appears within ___ s.
4. Playback, window 1 vs window 5 builds, for 5 minutes on 1h and then 48h. Count blank frames in loop 1 and loop 2+, check UI smoothness, device temperature and memory, and look for crashes.
5. Now repeat with alerts present, extras toggled on/off, palette switches, all layers, and map style switches. Also switch the server URL and background/foreground 10×. For the window-5 build these are the NSRangeException triggers; they must pass without crashes.
6. Scrub the slider quickly back and forth for 30 s.
7. Pan and zoom during playback. A GPS update must not recenter or reset the zoom. The Locate button works.
8. Widget: add it on the Home Screen, in tinted/clear appearance, in StandBy (night), and in CarPlay if available. Tapping it opens Radar from the killed state.
9. Watch: forecast page with the phone offline, and after a location change.
10. Android: gesture and 3-button nav, where the timeline must stay clear of the nav bar. Also predictive back on the style sheet and the alert modal, a tablet/foldable in landscape, and a 16 KB-page device or emulator.
11. VoiceOver/TalkBack: every control on the radar screen is labelled and reachable, at the largest text size.
