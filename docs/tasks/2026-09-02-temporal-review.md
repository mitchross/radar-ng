Cross-cutting:

- **`workflow_task_timeout`** (default 10 s) does not help the "scheduled, never started" case — it only bounds a task *after* a worker picks it up. Leave it. (The SDK did log one `[TMPRL1101] Potential deadlock detected: workflow didn't yield within 2 second(s)` — GIL starvation of workflow-task processing by CPU threads in the monolith; see §4.)
- **BUFFER_ONE** queues *behind* the stuck run — no help. **ALLOW_ALL** is unsafe: activities assume a single writer per layer (`backend/ingest_mrms/activities.py:5-7`). **TERMINATE_OTHER** would self-heal a stuck MRMS run at the next fire *without needing a worker* (terminate is server-side) and MRMS is safe to kill (immutable tile paths via `render_tiles_atomic`, ProcessedSet marked only after success, per-attempt tmp dirs `activities.py:223-235`). It is **not** safe for nowcast (9-min run would never finish). Recommendation: keep SKIP everywhere and rely on tight `execution_timeout`; optionally TERMINATE_OTHER on the two MRMS schedules only.
- **Jitter**: the three 2-min schedules fire on the same second (all `Spec every 2m`, jitter 0) → 3 simultaneous workflow starts, 2 MRMS renders each spawning a `ProcessPoolExecutor(2)` (`activities.py:329-330`) plus nowcast. 15–20 s jitter smooths CPU/memory peaks; cheap even after pool isolation.
- **Catchup window 1 h** with SKIP produces the 22-marker "buffered start" bursts after recovery (scheduler history 05:36:05Z) and the huge MissedCatchupWindow counters. For a 2-min poll, catching up is meaningless (each run lists the newest keys anyway). Use 5 m (2-min schedules), 10 m (5-min), keep 1 h for hourly+.
- **What tight timeouts do and don't buy**: during the 4-h DNS blackout they would have produced 120 TimedOut runs instead of 2 — no radar either way. They matter for the *single stuck run* class (orphaned pinned execution after a promotion, RUNBOOK.md:35-43; a lost activity task; a hung worker): recovery in 6 min instead of 90.

## 2. The 23:22Z incident, mechanically

History (`temporal workflow show sched-ingest-mrms-base-2026-09-01T23:22:00Z`): `1 WorkflowExecutionStarted 23:24:08Z → 2 WorkflowTaskScheduled 23:24:08Z → 3 WorkflowExecutionTimedOut 00:54:08Z` (HistoryLength 3, TaskQueue `radar-ng`, no build id). Note the start itself was 2 min late (nominal 23:22) — the scheduler was already lagging.

**What produces "WorkflowTaskScheduled but never Started"** — ranked by what the evidence supports here:

1. **Worker cannot reach the frontend (this incident).** The Python SDK's Rust core resolves `TEMPORAL_ADDRESS` (`temporal-frontend.temporal.svc.cluster.local:7233`, injected by the controller) on (re)connect. When both CoreDNS pods died (~23:25Z), the existing HTTP/2 channel broke (`h2 protocol error … Reset(StreamId(63), CANCEL, Remote)` appears twice in the worker log) and every reconnect failed with `dns error`. `temporalio_client::retry` retries `poll_workflow_task_queue`/`poll_activity_task_queue` with backoff **indefinitely and only at WARN/ERROR log level** — the process stays Running/Ready in k8s because the WorkerDeployment template has **no liveness or readiness probe** (`temporal-worker-deployment.yaml:50-86`; live pod: `liveness= readiness=`). The server, seeing a poller-less queue, simply parks the task in matching's backlog until the 90-min execution timeout.
2. **No poller on the routed queue (latent, radar-ng-specific).** `backend/api/api/routes_workflows.py:33,177` starts `WatchStormWorkflow` on `radar-ng-alerts`; `temporal task-queue describe --task-queue radar-ng-alerts --select-all-active` shows **zero pollers** because the worker runs `WORKER_ROLE=legacy` on `radar-ng` (`temporal-worker-deployment.yaml:72-75`). Today the routes are 503-gated (`routes_workflows.py:102-103`, no `WORKFLOW_AUTH_SIGNING_KEY`), so nothing is stuck yet — but the first enabled watch would sit at "scheduled" forever. Same class as RUNBOOK.md:35-43 (pinned execution whose build has no poller).
3. **Worker-side poller/slot starvation.** `max_concurrent_activities=4` / `max_concurrent_activity_task_polls=2` (`worker.py:84-85`); workflow-task pollers and `max_concurrent_workflow_tasks` are SDK defaults (5 pollers / 100 slots — verified against the installed SDK signature: `workflow_task_poller_behavior=PollerBehaviorSimpleMaximum(maximum=5)`). Slots are not the limiter for *workflow* tasks; the GIL is: CPU-heavy `asyncio.to_thread` work (pysteps, GRIB decode, PNG encode) starves the event loop and the workflow-task thread, hence the `TMPRL1101` deadlock-detector hit. This causes WorkflowTaskTimedOut + retry (seconds), not a 90-min stall.
4. **Sticky queue after a worker restart.** Tasks for cached workflows go to the dead sticky queue for `sticky_queue_schedule_to_start_timeout` (10 s default) before falling back — bounded, not this.
5. **Server-side task loss with `numHistoryShards: 1`** (`values.yaml:20`, live `temporal-config`). Today's DB move showed the failure mode in miniature: `Failed to load shard: GetOrCreateShard: failed to get ShardID 1 … no usable database connection`, `Queue reader unable to retrieve tasks: shard status unknown`, `Error updating queue state` ×51, `Fail to process task` ×125 in 7 minutes. With one shard, every namespace's transfer/timer queues share one reader; a DB flap pauses everything, and a task that exhausts the processor's retry budget is dropped. The **lost scheduler timers (§3)** are the chronic symptom of this class. It did not cause the 23:22Z stall (the DB was up; the server kept starting and timing out runs), but it is the platform risk.
6. **Matching partition/user-data load failure.** `Started/Stopped physicalTaskQueueManager` churned 50/37 times in the 05:15–05:22 window; with 4 default read partitions and 2 activity pollers, partitions without a poller rely on forwarding. Not implicated at 23:22Z.

**Changes that make radar-ng resilient regardless of cause:**

- **Worker liveness tied to Temporal reachability.** In `worker.py`, run a background coroutine that every 30 s calls `client.service_client.check_health()` (or `describe_namespace`) and touches `/tmp/temporal-healthy`; add `livenessProbe: exec: test $(find /tmp/temporal-healthy -mmin -3)` with `failureThreshold: 3` to the WorkerDeployment template. A restart would not have fixed DNS, but it would have surfaced `CrashLoopBackOff` instead of a green pod, and it does fix half-open channels.
- **Alert on the SDK's own signal.** Enable the Python SDK Prometheus runtime (`temporalio.runtime.Runtime(telemetry=TelemetryConfig(metrics=PrometheusConfig(bind_address="0.0.0.0:9464")))`) and alert on `rate(temporal_long_request_failure{operation=~"Poll.*"}[5m]) > 0 for 5m` and `temporal_worker_task_slots_available{worker_type="ActivityWorker"} == 0 for 10m`. That fires within minutes of a poll blackout; today nothing scrapes the worker.
- **Page on the existing alert.** `RadarNgObservedRadarStale` (`prometheusrule.yaml:13-20`) **did fire** 00:00–03:00Z (`ALERTS{alertname=~"RadarNg.*"}` = 1) and nobody was paged — Alertmanager routing, not detection, is the gap.
- **Tight execution timeouts** (§1) bound single-run stalls to ~2–3 cadences.
- **Kill the dead-queue trap**: set `TEMPORAL_ALERTS_TASK_QUEUE=radar-ng` on tile-server until the `alerts` role exists (`deployment-tile-server.yaml:96-99` only sets ADDRESS/NAMESPACE).
- **DNS plane hardening (infra repo):** CoreDNS runs 2 replicas (one on the control plane, one on gpu-workers) and both were down for 4 h; 3 replicas + `topologySpreadConstraints` + a PDB, and consider Cilium's node-local DNS cache. As a worker-side belt-and-braces, `hostAliases` pinning `temporal-frontend.temporal.svc.cluster.local` to the Service ClusterIP (`10.100.177.12`, stable for the Service's lifetime) removes the DNS dependency for the one hostname that matters — document the coupling if you do it.
- **Server metrics are not scraped at all** (`count({namespace="temporal",__name__=~"service_requests.*|persistence_requests.*|poll_success.*"})` is empty; only `servicemonitor/temporal-postgres` exists). Chart knob: `server.metrics.serviceMonitor.enabled: true` (`charts/temporal-1.6.0/temporal/values.yaml:40-41`). Then alert on `no_poller_tasks`, `task_schedule_to_start_latency`, `persistence_error*`, `schedule_missed_catchup_window` (§5).

**What it does** (`seed.py`):

**Correctness issues in the current code:**
1. **Unconditional update on every worker restart** (`:225-234` always returns a `ScheduleUpdate`). Given the correlation above, every restart pokes 16 scheduler workflows. Return `None` (no-op) when `inp.description.schedule.spec/action/policy` already equal the desired spec.

4. `print()` instead of the worker's `loguru` logger (`:221,236,260,280,307,358,368`) — these lines are invisible to any log-level filtering.
5. Tests (`test_seed.py`) cover the terminate path only; nothing exercises `_recreate_wedged` or the retry loop.

**What to add so wedges self-heal (small, this week):** a *watchdog* coroutine in `worker.py` (only in the seeding role): every 60 s, for each `ScheduleDef`, `handle.describe()`; if `info.next_action_times[0] < now - 2×interval` and `not info.running_actions` → log at ERROR and call `handle.trigger(overlap=ScheduleOverlapPolicy.SKIP)`. The `describe` alone is the kick (proven tonight), `trigger` makes the overdue run happen immediately. Expose a counter for the alert rule. Until then the operator-level equivalent is `temporal schedule describe --schedule-id <id>` for `poll-alerts`, `weekly-trend-digest`, `daily-news-digest` (the last two are news-reader's and are wedged right now: `NextRunTime 1 day ago`).

## 4. Worker process design and the isolated-queue rollout

**Current monolith** (`worker.py`): one asyncio process on `radar-ng`, `max_concurrent_activities=4`, 2 activity pollers (`:84-85`); every heavy activity runs via `asyncio.to_thread` in the default executor (GIL-bound) except MRMS palettes, which fork a `ProcessPoolExecutor(MRMS_RENDER_WORKERS=2)` per frame (`backend/ingest_mrms/activities.py:62,329-330`) and pickle a ~60 MB array per palette (`:322-327`). Concurrency intents fight the 4 slots: MRMS `FRAME_CONCURRENCY=2` ×2 schedules (`ingest_mrms.py:45`), HRRR `FORECAST_CONCURRENCY=8` (`ingest_hrrr.py:40`), AQM `CHUNK_CONCURRENCY=2` (`ingest_airquality.py:46`), lightning holding one slot 50 min/h (`ingest_lightning.py:27`) — prior review H5 still open. Memory: Prometheus `container_memory_working_set_bytes{container="worker"}` saw-tooths 3.0→9.4 GiB in 5-min steps (17:30–18:50Z Aug 31), and the OOMKilled container's tail shows AQM chunks (813 s), HRRR fan-out, nowcast, two MRMS frames and lightning all active 18:41–18:49Z. `kubectl top` now: 4.2 CPU / 5.4 Gi; requests are `250m / 3Gi`, limits `12 / 12Gi` (`temporal-worker-deployment.yaml:85-86`). `run_sync_with_heartbeat` (`activity_heartbeat.py:16-38`) cannot cancel the thread it started — a heartbeat-timeout cancel only stops the beater (`:36-38`); the pysteps thread keeps the CPU and the slot until it finishes (prior H7b, open).

**Verified controller behaviour that changes the design:** the rendered `deploy/radar-ng-worker-v1-1-24-f58c` **keeps** `podAffinity.requiredDuringSchedulingIgnoredDuringExecution → app: tile-server` (`kubectl get deploy … | grep -A12 affinity`). The comment "the WorkerController strips podAffinity" (`deployment-open-meteo.yaml:53`, echoed in `kustomization.yaml:18`) is contradicted by the live object under controller v1.9.0 (`infrastructure/controllers/temporal-worker-controller/values.yaml:14`). Co-location via podAffinity works for WorkerDeployments; the open-meteo sidecar workaround is optional.

## 5. Temporal server platform risks (homelab)

- **`numHistoryShards: 1`** (`values.yaml:20`, live cm). Immutable after first boot (chart comment `charts/…/values.yaml:142`). One shard = one timer queue, one transfer queue, one visibility queue for **all** namespaces; a DB flap or a `history` pod restart pauses every workflow; a poison task blocks everything; the lost scheduler timers (§3) are the chronic cost. **Migration plan** (cheap here because durable state is on PVCs, `ARCHITECTURE.md:83`): stand up a second release (`temporal-v2` namespace, `numHistoryShards: 32–64` — 512 is oversized for 500 m-CPU pods, fresh Postgres), seed namespaces `radar-ng`, `deal-scout`, `news-reader`; point `Connection/cluster-temporal` (`temporal-connection.yaml:8`) and the tile-server/open-meteo env at the new frontend; the worker's own `seed_with_retry` recreates every radar-ng schedule on first start. Pause the old schedules first (`temporal schedule toggle --pause`) so both clusters never fire into the same PVC. Only long-lived state to consider: `WatchStormWorkflow` entities (0 Running today) and deal-scout/news-reader's own workflows (their owners re-seed).
- **Dedicated `radar-ng` namespace — already exists** (`scripts/seed-namespaces.sh:42`; `operator namespace list` shows it) and is unused. Benefits: its own `temporal-sys-per-ns-tq` internal worker (the 16-schedule update burst at 18:52Z produced `WorkflowTaskTimedOut` ×2 on tile-cleanup's scheduler and the server worker logs `LocalActivity completed after activity deadline`), per-namespace RPS/retention/visibility isolation from deal-scout/news-reader. Change: `WorkerDeployment.spec.workerOptions.temporalNamespace: radar-ng` (`temporal-worker-deployment.yaml:15`), `deployment-tile-server.yaml:98-99`, `deployment-open-meteo.yaml:66-67`; pause+delete the 11 `default` schedules after the first seed in `radar-ng` (double-firing otherwise). Retention: 168 h (`seed-namespaces.sh:52`) is generous for ~4,300 closed runs/day of throwaway histories on a 10 Gi Postgres PVC; 72 h for `radar-ng` via `temporal operator namespace update --retention 72h`. **Archival** is `disabled` (live cm) — keep it that way; nothing here needs history after 72 h.
- **Postgres** (`postgres/deployment.yaml`): single replica, `Recreate` (`:13-14`), 100 m / 256 Mi → 1 Gi (`:78-83`), RWO Longhorn **with `numberOfReplicas=1`** (`kubectl -n longhorn-system get volume pvc-fcfecb3b… → replicas=1`), so a disk/node loss = lose the control plane's state (kopiur hourly restore is the only copy, `kopiur/temporal-postgres-data.yaml:56`). VPA `InPlaceOrRecreate` on cpu+memory with `maxAllowed 2 / 2Gi` (`vpa.yaml:12-25`); it did **not** cause tonight's move (node reboot did), but Recreate fallback on a DB is an outage you schedule for yourself. Recommend: `updateMode: "Off"` for `temporal-postgres` and `temporal-history` (`vpa.yaml:12-14, 103-105`) — keep the others; bump Postgres to `500m / 512Mi → 2Gi` (VPA upperBound is 383 Mi so headroom is real); co-locate DB and server on one node with `podAffinity` (preferred) so a reboot is one outage, not two (all 7 Temporal pods are on gpu-workers, DB is now on hp-elite); consider Longhorn `numberOfReplicas: 2` for this one 10 Gi volume (accept the "replicas=1 everywhere" rule exception or don't — but write it down); **no** `minAvailable: 1` PDB on single-replica pods (blocks Talos drains, per CLAUDE.md). Make the kopiur `CHECKPOINT` hook (`:26`) explicit about the IO stall it induces at :06 hourly.
- **Worker Controller** (v1.9.0, 1 replica, `ALLOWED_KINDS=HorizontalPodAutoscaler`): every reconcile calls `DescribeWorkerDeployment` through the frontend; tonight it logged 51 `context deadline exceeded` during the DB move and recovered — not a rate-limit problem at 3 WDs. Real risks are the identity dance in RUNBOOK.md:3-33 and Progressive rollouts needing two pods on the RWO node (the reason for the `250m` request hack, `temporal-worker-deployment.yaml:83-85`). Use `AllAtOnce` for single-replica RWO roles.
- **Dynamic config is empty** (`temporal-dynamic-config` cm `dynamic_config.yaml: ""`; chart renders `server.dynamicConfig`). Worth setting for a 1-poller-per-queue homelab: `matching.numTaskqueueReadPartitions: 1`, `matching.numTaskqueueWritePartitions: 1` (defaults 4 → with 2 activity pollers some partitions have no poller and rely on forwarding, adding schedule-to-start latency). Don't touch history queue tunables blind; get metrics first.
- **Prometheus alerts to add** (after `server.metrics.serviceMonitor.enabled: true` and the SDK Prometheus runtime):
  - Schedule missed: `increase(schedule_missed_catchup_window[15m]) > 0` (server `worker` service; the log line `Schedule missed catchup window` appeared 552× since 03:08Z today).
  - Workflow task schedule-to-start: `histogram_quantile(0.95, sum by (le,taskqueue) (rate(task_schedule_to_start_latency_bucket{taskqueue=~"radar-ng.*"}[5m]))) > 60` (matching).
  - Activity schedule-to-start (SDK): `temporal_activity_schedule_to_start_latency` p95 > 60 s per `task_queue`.
  - Worker slots: `temporal_worker_task_slots_available{worker_type="ActivityWorker"} == 0 for 10m`.
  - Request failures: `rate(temporal_long_request_failure{operation=~"Poll.*"}[5m]) > 0 for 5m` (SDK) and `rate(service_error_with_type{error_type!~"NotFound.*"}[5m]) > 0 for 5m` (frontend); `rate(persistence_error_with_type[5m]) > 0 for 5m` (history).
  - Poller absence: `no_poller_tasks > 0` (matching) — would have caught the dead `radar-ng-alerts` queue and the DNS blackout.
  - App-level catch-all for wedges of any cause: have the tile-server export `radar_ng_state_file_age_seconds{file}` for `alerts_active_snapshot.json`, `lightning.json`, `nowcast-status.json` and alert > 2× cadence; the existing `radar_ng_mrms_age_seconds` rule proved the pattern works.
  - Route `severity: critical` to a receiver that pages (Alertmanager); the 3-hour firing tonight went nowhere.
- **DNS plane**: 2 CoreDNS replicas both down for ~4 h is the single largest outage cause observed; 3 replicas + spread + PDB, and node-local caching (infra repo).

## 6. Best-practice deltas

| Area | Finding (file:line) | Delta |
|---|---|---|
| Determinism | Workflows import activity modules under `workflow.unsafe.imports_passed_through()` (all `workflows/*.py`); no `datetime.now`, randomness or I/O in workflow bodies; `asyncio.Semaphore`/`gather` inside workflows are the sandbox-patched versions — fine. `open_meteo_sync.py:20` imports `task_queues` outside the passthrough — pure constants, fine. | Add `temporalio.worker.Replayer` replay tests against a few exported histories in CI. |
| Versioning | `WorkerDeploymentConfig(use_worker_versioning=True, default_versioning_behavior=PINNED)` (`worker.py:211-215`). PINNED for seconds-long scheduled workflows buys nothing and creates the RUNBOOK.md:35-43 orphan failure whenever a build is retired mid-run. | Default `AUTO_UPGRADE`; `@workflow.defn(versioning_behavior=VersioningBehavior.PINNED)` only on `WatchStormWorkflow` (entity, days-long). Keep `workflow.patched()` for in-place changes to WatchStorm. |
| Activity idempotency | Good: atomic tile staging (`render_tiles_atomic`), per-attempt tmp dirs (`activities.py:223-235`), ProcessedSet marked after success, flock'd manifest (`manifest.py:109-116`), `mark_alerts_seen` idempotent (`storm_watch_activities.py:338-360`), only `radar` writes `storms.json` (`activities.py:301-307`). | `_render_all` uses `ProcessPoolExecutor` from an asyncio thread with Python 3.12's fork default (prior M11) — set `mp_context=multiprocessing.get_context("spawn")` or `forkserver`. |

| Local activities | `hrrr_horizon_for_run` (10 s, pure function of run id, `ingest_hrrr.py:89-93`) and `detect_storm_change` (pure, `watch_storm.py:140-150`) are network round-trips for no reason. | Inline as plain functions (they are deterministic) or `workflow.execute_local_activity`. Keep tiny file writes (`*_mark_processed`) as normal activities — they are I/O. |
| `wait_condition` | `watch_storm.py:155-161` uses `wait_condition(..., timeout=60s)` as the poll interval — correct. But `_pending_alert_id` is a single slot (`:91-92`): two `alertMatchSignal`s before the loop drains lose one. `continue_as_new(inp)` (`:114`) drops `WatchStormState` and any buffered signal (prior M13, open). | Use a `deque`; pass state in `continue_as_new` args; `workflow.all_handlers_finished()` before CaN. |
