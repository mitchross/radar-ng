# Post-migration review: 2026-10-14

Reviewed `d07116a` and production v2.0.1. Runtime observations were collected around 03:11–03:18 UTC on October 15.

## Findings

### P1: nowcast rendering can deadlock

Production had 27 threads waiting in `locks_lock_inode_wait`. Open file descriptors pointed to nowcast publication lock stripes.
Temporal history for `sched-nowcast-2026-10-15T02:51:16Z` records a 600-second StartToClose timeout. Several preceding runs also failed.
The worker had two restarts. Its latest termination was `OOMKilled` with a 12 GiB memory limit.

`render_all` parallelized leads on a Rayon pool. Each lead held publication locks while scheduling parallel tile work on that same pool.
A stolen lead can wait on a lock held by suspended work. Sorted lock acquisition does not prevent this scheduler dependency.

A local 72-lead regression test exceeded a 25-second timeout before the fix. After the fix, it completed in 2.21 seconds.
Leads now render in order; tiles still use the configured worker pool. Production recovery requires a new release and GitOps image update.

Cancellation drops the async future, but blocking work continues. This can retain memory across timeouts; its contribution to the observed OOM remains unmeasured.
See [Tokio blocking-task semantics](https://docs.rs/tokio/latest/tokio/task/fn.spawn_blocking.html).

### P1: expired nowcasts appear current

At 03:12 UTC, the point API returned `status: ok` for a run issued at 01:56 UTC, ending at 02:56 UTC.
The web displayed “No rain expected for the next hour.” Health also returned `ok`, using a status file last updated at 01:57:41 UTC.

The API now returns `unavailable`, `nowcast_expired`, and no points when no published frame remains in the future.
The expiry check precedes cache lookup. Health returns 503 with `nowcast_expired` for the same condition.
This change does not diagnose missing status files or impose an age limit on partially expired runs.

The web already hides next-hour content with no points. The app already rejects unavailable radar nowcasts and uses its existing fallback.
Both clients receive the server correction automatically. No native rebuild is required for these backend-only changes.

### P2: push registration remains unavailable in production

The tile-server mounts `/data/state` read-only. The API writes push tokens directly to SQLite and returns 503 for read-only storage.
This limitation was already documented in the migration handoff materials. No authenticated registration request was sent during this review.
Changing the persistence design or mount requires a separate decision and GitOps change.

### P2: frontend CI fails dependency validation

GitHub run `38628937781` reports 11 Expo dependency mismatches. The failures include `react-native-screens`, Expo, and `@expo/ui`.
This is separate from the backend changes. Dependency versions were not changed during this review.
